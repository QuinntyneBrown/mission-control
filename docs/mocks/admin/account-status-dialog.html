Administrator-only. Shown for Ada Okafor, as opened from Deactivate on her details page or her row in Accounts. Focus starts on Cancel, the safe choice. Deactivation keeps the account, its assignments, and its audit history; Ada's existing token is refused on the next request. Success shows the toast "Account deactivated: Ada Okafor can't sign in. Their assignments are kept."

Reactivation restores sign-in with the existing password and the same role. Success shows the toast "Account reactivated: Jordan Reyes can sign in again."

Opens from a Deactivate or Reactivate action. The dialog reads the account first for its name, email, role, and version, so the title stays generic and Deactivate account stays disabled until the record arrives; Reactivate loads the same way. Cancel closes without sending anything. Screen readers hear "Loading account…"; focus stays on Cancel. A read that answers 404 closes the dialog: from the account's page, that page shows Account not found; from the list, the list reloads and announces that the account wasn't found.

The read failed, so Deactivate account stays disabled and nothing was changed. Try again repeats the read and names the account once it arrives. This read answered 500, so the reference ID matches the server's diagnostic record; a read that got no response shows "Check your connection and try again." without a reference ID. The alert is announced and focus moves to Try again; Cancel closes without sending anything.

The interface never offers Deactivate for the designated administrator. This is the API's 409 answer when the request is made anyway, for example from an outdated page. The rejected attempt is recorded in the audit log with outcome Rejected. Nothing changed, so the only action is Close. Deactivate account, which had focus, is gone, so focus moves to Close, and screen readers hear the explanation as an alert; it is also the dialog's description.

Both buttons wait while the request is in progress, so the action can't be sent twice. Focus stays on the busy Deactivating… button.

The API answered 500, or 503 because it was busy, so nothing changed: Ada can still sign in. Try again repeats the same request; the reference ID matches the server's diagnostic record. The alert is announced and focus stays on Try again. A refused request (400) shows the API's reason in this alert instead, without Try again or a reference ID; Deactivate account is gone, so focus moves to the alert. A request that gets no response may have been applied, so it changes this presentation: the dialog first re-reads Ada's account, with both buttons disabled, so focus moves to the alert. If she is already inactive, the change is in place and the dialog closes with the "Account deactivated" toast. Otherwise the alert reads "We couldn't confirm the deactivation", with no reference ID and never "nothing changed", and Try again sends the change with the latest version. The page behind rereads at once while the dialog stays open, so Cancel just closes. If the API answers 403 because you're no longer an administrator, the dialog closes and the access-denied page replaces Accounts.

The account changed after the dialog opened, for example another administrator changed its role, so the API answered 409 and nothing changed. The request is never resubmitted automatically; Review account closes the dialog onto Ada Okafor's latest details (/accounts/:id), where the action can be chosen again, and Cancel closes and rereads the page behind. Deactivate account, which had focus, is gone, so focus moves to Review account, and screen readers hear the explanation as an alert; it is also the dialog's description. When this answers a Try again after a deactivation that got no response, the explanation leaves out "Nothing was changed", because the first request may be the change it reports.
