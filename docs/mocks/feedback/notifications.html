Feedback · Notifications and pop-ups All mocks

The toasts, alerts, and menus on this page are static specimens and are not announced. "Show" pushes a live copy into the toast region at the bottom of the screen.

Up to three toasts stack bottom-right, newest last; below 576px they span the bottom of the screen. The error stays until dismissed or retried; focus never moves to a toast. The toast region always holds two live containers, a polite status container for success and info and an alert container for errors and warnings, so a new toast is announced by the container it joins; a toast itself carries no role. While a dialog is open, the toast region stacks above it in the overlay layer, outside the background the dialog makes inert, so both live containers keep announcing; below 576px it sits above a sheet's pinned footer, so no toast covers the footer's actions, and the sheet keeps a focused field scrolled clear of the toast. A toast's own actions become reachable once the dialog closes.

Feedback catalog

Notifications and pop-ups

Every message, confirmation, and pop-up the application uses, with when it appears and how assistive technology hears it.

How feedback behaves

  • A toast confirms an outcome the page already shows. It never holds the only copy of something important.
  • The page where the action happened raises its toasts and the application shell displays them. Every toast clears when the session ends. Losing the connection shows the offline banner, never a toast.
  • Success and info toasts dismiss after 8 seconds, waiting while hovered or focused. Errors, warnings, and toasts with an action stay until dismissed.
  • Outcomes are announced through a polite status region; failures use an assertive alert. Focus stays where the person was working, unless the outcome disables or removes the focused control: then focus moves to the outcome's alert or its first offered action. Validation with several problems focuses the error summary; a single problem, or a server 400 naming one field, focuses that field, which reads its error.
  • Status is never colour alone: every tone has an icon and words.
  • Destructive confirmations name the affected item and offer a clear way back.

System

  • Your access changed

    You no longer have permission to do that.

    Shown when
    The API unexpectedly answers 403 to an action that needs only an active session: a card move, adding, editing, or reordering work, or planning, starting, re-scoping, or closing a sprint. The page where it happened puts back what was last saved and raises this toast; there is no Retry, because repeating the action would be refused again, and the person's permissions refresh. Administrator-only dialogs explain a 403 inside the dialog, and Accounts or the Audit log show the access-denied page instead. A deactivated account gets 401 and the sign-in page's “Your session ended” message.
    Tone and announcement
    Error · Alert (assertive) · Stays until dismissed

Banners and inline alerts

Persistent messages inside a page or dialog. Page banners sit under the page header.

  • Info

    Your session ended

    For your security, sessions end after 30 minutes or when the page reloads. Sign in to continue.

  • Success

    You've signed out

    Sign in again whenever you're ready.

  • Warning: edit conflict

    This lead changed after you opened it

    Your edits haven't been saved. Compare them with the latest saved version, then reload it and re-apply what you need.

    See it in the form After Reload latest

    Shown when a save answers 409 because the record changed after the form opened. The form keeps your values beside the latest saved ones and never resubmits; Reload latest loads the latest values and keeps the comparison visible. When the save follows one that got no response, the first save may be the change shown, so the alert is headed "The latest saved version is shown beside your entries" instead and never says "Your edits haven't been saved".

  • Error with reference ID

    We couldn't save this lead

    Nothing was saved, and your entries are still here. Try again.

    Reference ID b84d-2f61-0c9e

    Shown when a save answers 500, or 503 when the server is busy. A save that gets no response may still have been made, so the same alert reads "We couldn't confirm whether …" with no reference ID and never says nothing was saved; the form reads the saved record again before another attempt.

  • Neutral: read-only

    You can view leads. Only administrators can add, edit, or delete them.

  • Offline banner

    You're offline

    What's on screen stays, but changes can't be saved until you reconnect.

    The application shell shows this banner while the latest request got no response, and clears it with the next response. Content already on screen stays. Try again reloads the current page in place (the address stays), so its views are recreated and read their data again; a form with unsaved input asks first. There is no offline toast.

  • Board changed

    The board changed

    The board changed after it loaded, so your move wasn't applied. Reload to see the latest board.

    Shown at the top of a Kanban or sprint board when the API refuses a move with 409 because the board changed after it loaded. The board keeps its last saved view, and Reload board reads the latest columns; nothing is resubmitted. It is a page alert, not a toast. See it on the Kanban board.

  • Access changed in an administrator dialog

    Only administrators can add or edit leads

    Your access changed while this form was open, so nothing was saved. Your entries are still here.

    Shown inside an administrator-only dialog when its save answers 403 because the role changed while it was open: that dialog's designed 403, such as the lead form's forbidden state. The title names what only administrators can do there. The dialog stays open with every value and its save action becomes unavailable, so focus moves to this alert; it offers no action, Retry, or reference ID. After a save that got no response, the text reads only “Your access changed while this form was open. Your entries are still here.”, because the first save may have gone through. A change any active account may make shows the “Your access changed” toast instead. See it in the lead form.

  • Sprints paused in Kanban

    Sprints are paused while this project uses Kanban

    Sprint 3 (planned) and the history of Sprints 1 and 2 are kept. An administrator can switch Prayer Wall App back to Scrum to use them.

  • Sign-in paused

    Too many sign-in attempts

    For your security, sign-in for this email is paused. Try again after 3:42 p.m. (in about 12 minutes).

    The time comes from the 429 response's retry timing, the remaining pause, so it is never a fixed 15 minutes.

  • Blocked action

    Grace Mensah can't be deleted yet

    Grace is the responsible lead for Prayer Wall App. Choose another responsible lead for that project first.

Dialogs and confirmations

Every dialog moves focus inside, keeps Tab within it, closes with Cancel or Escape, and returns focus to what opened it. Below 576px form dialogs become full-screen sheets with a pinned footer; confirmations stay centered with full-width stacked actions and name the item.

  • Delete lead Confirmation naming the contact, or a blocked explanation.

  • Change delivery mode Confirmation, or blocked while a sprint is active.

Focus

A 2px ring with a 2px offset on every focusable control, at 3:1 contrast or better against its surroundings. Fixed bars never cover the focused element.

Screen-reader announcements

Outcomes are announced without moving focus, with two exceptions. When an outcome disables or removes the focused control, focus moves to the outcome's alert or its first offered action. Validation with several problems moves focus to the error summary, and a single problem, or a server 400 naming one field, moves focus to that field.
