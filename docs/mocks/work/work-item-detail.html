The detail is a project tab route, so the pinned project header and tabs render here too, with Work active; on phones only the tabs stay pinned. Under them, the parent path lists the item's ancestors from its initiative down, and each ancestor opens its own detail view. In the mock, ancestors without a detail state of their own open the project outline instead. Below 576px a task's middle levels fold into the "…" menu. After navigation, focus moves to the item's heading. Updating the status to Done while tasks are unfinished asks for confirmation first. Every other status change, from this control or a task row's status, saves only the new status with the version the page loaded; the detail and its tasks then reload, and the change is announced, for example "Add team capacity limits marked Done". If the item changed since it loaded, the update answers 409 and the detail reloads the story and its tasks once and announces that it changed; nothing is resent.

Update status sent Done, and the API answered 500, or 503 because the project was busy, so nothing changed. The status control returns to the saved status, In Progress, and the alert under it is announced with the reference ID. Focus stays on Update status; Try again resends the same request, and nothing retries automatically. If the retry finds unfinished tasks, the confirmation opens as usual. Any other status change that fails this way, from this control or a task row, shows the same alert with its own reference ID; for a task the alert appears under that task's row, and its status returns to the saved value. A status change that gets no response may have saved, so the detail and its tasks reload once and the control shows the saved status; this alert then reads “We couldn't confirm the status change” and names the saved status, for example “Volunteers can join a build team is In Progress now.”, never “Nothing changed”, with no reference ID or Try again, any open confirmation closes, focus returns to the status control, and the saved status is announced. If that reload fails, the page shows the Load failed state. Changing status needs only an active session, so a 403 is unexpected: the control returns to the saved status without this alert, any open confirmation closes, and the page shows the "Your access changed" toast, without Retry or a reference ID. A status change or completion the API refuses (400, for example a malformed request or an item that isn't a story) keeps the saved status and shows the server's message under the control, linked to it, with no Try again or reference ID, because sending it again would be refused again; focus stays on the control, which reads the message.

Initiatives are the top level. They have no parent and no "Move to another parent" action. Initiatives and epics are not estimated and don't join sprints.

Each epic belongs to one initiative in the same project. Its stories keep their own sprint membership. The count comes from the detail's child count, never from the rows on screen. The mock draws the first 4 of the 14 stories to show Load more; in the product each batch holds 25, so Load more appears only while more stories remain. Load more keeps focus on the button and announces how many more loaded; when the last batch loads, the button goes away, so focus moves to the first newly loaded story.

Tasks follow their story's sprint and have no estimate of their own.

Optional values that are empty are labelled, never left blank.

The title was saved as typed. It shows as plain text and never runs as code. Inactive people keep existing assignments but aren't offered for new assignments; an item's current inactive assignee stays selected in the edit form until changed.

Collaborators can edit, change status, and move work. The page passes the layout's canDeleteWork (false without work.delete) to the detail view, so Delete is disabled with its reason. The project header shows the same notice as every project tab, and Project actions is absent.

The ID in the link doesn't exist or the item was deleted, so the read answered 404 and nothing about the item is known. The project header still shows the project, which loads separately; the page offers the project's work and the project list. A malformed ID in the link, such as …/work/not-an-id, shows this same Not found state. When the project itself no longer exists, the 404 says so instead: the header keeps only the breadcrumb and the page shows "Project not found" with Back to projects and no Try again or reference ID, the same presentation as the project overview's Not found state. A status change or completion that answers 404 because the item or its project was deleted meanwhile rereads once and lands on whichever of these two presentations the read reports, with focus on its heading; a task deleted meanwhile just leaves the tasks list, and because its status select went with it, focus moves to the Tasks heading.

A skeleton holds the layout while the item loads. Screen readers hear "Loading work item".

The item couldn't load (a 500, a busy 503, or no response), which is different from an item that doesn't exist. Try again reloads the item, and the project header rereads with it in case it failed too. The reference ID appears only when the server answered and matches its diagnostic record; with no response there is none.
