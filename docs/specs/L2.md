# L2 - Detailed Requirements

**Status:** Detailed baseline drafted against the confirmed [L1 scope](L1.md).  
**Sources:** [PRD](../PRD.md), [AGENTS.md](../../AGENTS.md), and the product owner's
explicit exemption for design artifacts.

## Reading and verification conventions

Each numbered requirement traces to exactly one L1. Production behavior must be
delivered with acceptance tests written before implementation; each acceptance
test file must include a comment listing its covered L2 IDs. Backend acceptance
checks use API integration tests; frontend checks use Chromium Playwright and
page objects as required by AGENTS.md.

**Design artifact exception:** L2-047 and L2-048 are evaluated by manual review.
Mocks and the design system must not use ATDD, and no tests must be written for
them. Their Given-When-Then criteria describe review outcomes, not test obligations.
Production application tests can use mocks as dependencies without testing the
mocks themselves. Do not create architecture or specification-parsing tests.

## Proposed elaboration defaults

These defaults make criteria concrete. They are proposed L2 decisions, not claims
that the product owner previously approved the PRD's proposals. Changes must update
the affected requirements and their production acceptance criteria together.

| Topic | Proposed baseline |
| --- | --- |
| Roles | Administrator and Collaborator, using the PRD permission matrix |
| Lead records | One category per record; multiple records per category; unique normalized email/category pair |
| Contact validation | First/last name and email required; phone optional; limits in L2-009 |
| City contact | Seed a separate Quinntyne Brown City lead with no invented phone |
| Workspaces | Toronto projects with Kanban or Scrum mode; authenticated users have read access |
| Work fields | Required title; optional description, assignee, dates, and nonnegative story estimate |
| Board | Stories as cards; To Do, In Progress, Done; tasks inside stories; no WIP limits in this baseline |
| Scrum | One active sprint per workspace; one open sprint per story; tasks inherit story membership |
| Sessions | Signed JWT access tokens, 30-minute lifetime, in-memory client storage, no refresh tokens; login after reload/expiry |
| Accessibility | WCAG 2.2 AA target, with the concrete controls in L2-033–L2-035 |
| Initial load | 1,000 leads, 10,000 work items across 50 projects, 25 concurrent users |

SQL engine, supported framework versions, hosting, and deployment topology remain
design decisions. Their selection must preserve the behavior below. Performance
environment requirements are specified in L2-046 rather than left implicit.

**Responsive profile R:** Viewport widths 320, 375, 576, 768, 992, 1200, and 1920
CSS pixels, each with an 800-pixel height. XS is <576px, small 576–767px, medium
768–991px, large 992–1199px, and XL ≥1200px. All UI criteria also apply under
L2-030; no UI-facing requirement is exempt from this profile.

**Permission profile P:** Administrator can perform every operation. Collaborator
can read contacts/workspaces/work, create and update work, prioritize backlogs,
move cards, and plan/start/close sprints. Collaborator cannot mutate lead contacts,
create/edit/delete workspaces, delete work, change project mode, manage accounts,
or configure boards. Account provisioning is private; public registration is absent.

**Common validation V:** Trim required text; whitespace-only values are invalid.
Normalize email for comparison by trimming and case folding. Required-field,
length, malformed-value, and invalid-reference errors return HTTP 400 with field
messages. Permission failures return 403, missing/invalid authentication returns
401, missing records return 404, and conflicting changes return 409. A rejected
mutation must leave persistent state unchanged. API responses must not expose
password hashes, credentials, signing keys, or internal exception details; a
successful login response contains its intended access token.

## L2-001: Credential login
**Traces to:** L1-001

The application must authenticate SQL-backed active users by email and password.

**Acceptance Criteria:**
1. Given an active account and valid credentials, when login is submitted, then the API returns a signed access token with its expiry and the UI opens the home workspace.
2. Given an unknown email, wrong password, or inactive account, when login is submitted, then the API returns 401 with the same generic message and does not create a session.
3. Given a normalized account email, when login uses different letter case or surrounding email whitespace, then it identifies the same account; password whitespace must not be altered.
4. Given profile R, when login is completed at each width, then labels, inputs, errors, and the submit control remain accessible without page horizontal scrolling.

---

## L2-002: JWT validation and current access
**Traces to:** L1-001

The API must validate signature, configured issuer/audience, subject, and expiry,
and evaluate current account status and permissions in SQL for protected requests.

**Acceptance Criteria:**
1. Given a correctly signed unexpired token for an active user, when a permitted protected operation is requested, then access succeeds under profile P.
2. Given an absent token, malformed token, changed signature, wrong issuer/audience, or expired token, when a protected endpoint is requested, then it returns 401 without changing data.
3. Given a token with a deleted or inactive user subject, when it is presented, then access returns 401 even if its expiry has not been reached.
4. Given a user's permissions changed after token issuance, when the next request is processed, then the API uses the current SQL permissions and returns 403 for an operation no longer permitted.

## L2-003: Session expiry and logout
**Traces to:** L1-001

The client must hold the token in memory, clear it on logout, and require login
after reload or expiry. Local logout does not revoke a copied valid access token.

**Acceptance Criteria:**
1. Given a successful login at time T, when the token is inspected, then its expiry is T plus 30 minutes; requests at or after that expiry return 401.
2. Given a signed-in session, when logout is selected, then the token and protected cached data are cleared and navigation returns to login.
3. Given an expired session or browser reload, when a protected route is opened, then login is required and no contact/work data is shown until authentication succeeds.
4. Given a form with unsaved input when expiry occurs, when login is required, then the UI explains that unsaved changes were not persisted and does not report a successful save.
5. Given profile R, when the user signs out at any width, then the logout action is reachable and the result is visible.

---

## L2-004: Administrative account management
**Traces to:** L1-001

Administrators must provision active users, edit names and roles, set a replacement
password, and deactivate/reactivate accounts. Users must have unique normalized
email, first name, last name, and a role from profile P. Names must be 1–100
characters and email must be a syntactically valid address of at most 254
characters. Proposed password policy: new or replacement passwords must be
12–128 characters, without trimming. Account deletion is outside this baseline;
deactivation preserves work assignments and audit identity.

**Acceptance Criteria:**
1. Given an administrator and valid new account details, when provisioning is confirmed, then one SQL-backed account is created and the supplied password permits login.
2. Given an existing normalized email, unknown role, missing required field, exceeded field limit, or password outside the stated bounds, when provisioning is attempted, then a duplicate returns 409 or invalid fields return 400, with no new account.
3. Given an ordinary account, when an administrator changes its role or status, then the next protected request and next login reflect that change.
4. Given an account password is replaced, when login uses the old password, then it fails; login with the replacement succeeds and previously issued tokens are invalidated.
5. Given a Collaborator or unauthenticated caller, when account management is attempted through UI or API, then controls are unavailable and the API returns 403 or 401 respectively.
6. Given profile R, when an administrator provisions or updates a user, then validation, confirmation, and completion feedback remain usable at every width.

## L2-005: Permission enforcement and contact/account separation
**Traces to:** L1-001

The API and UI must apply permission profile P. Lead category or contact creation
must not create a login or change a user's authorization.

**Acceptance Criteria:**
1. Given each role in profile P, when every listed operation is requested directly, then permitted operations succeed and forbidden operations return 403 without mutation.
2. Given a lead is created in any of the five categories, when accounts and roles are read by an administrator, then no account or permission was added by that operation.
3. Given a lead contact has no account, when its email is submitted to login, then login returns the same generic failure as an unknown account.
4. Given a Collaborator at profile R, when a restricted screen or record is viewed, then mutation controls are hidden or disabled with a readable explanation; direct API calls remain denied.

## L2-007: Repeatable and repairing administrator seed
**Traces to:** L1-002

The seed must avoid duplicates, preserve existing passwords and restore the
designated account's active status and highest capabilities.

**Acceptance Criteria:**
1. Given an existing designated account with a changed password, when initialization runs repeatedly, then its ID and password hash remain unchanged and its account count remains one.
2. Given two instances initialize the same database concurrently, when both complete successfully, then exactly one designated account exists and both report readiness.
3. Given the designated account was made inactive or lost administrator capabilities through an out-of-band database change, when initialization completes, then it is active with highest capabilities and its existing password is preserved.
4. Given a future capability is added to the administrator role, when the designated account is evaluated, then it has that capability without creating a second role assignment or account.

## L2-008: Protect the designated administrator
**Traces to:** L1-002

Application operations must not delete, deactivate, demote, or change the email
identity of the designated administrator. Its password can be replaced securely.

**Acceptance Criteria:**
1. Given an administrator requests any prohibited change to the designated account, when it is submitted through the API, then it returns 409 with an explanation and preserves the account's identity and access.
2. Given the designated account is shown in account management, when viewed under profile R, then its protected status is explained and prohibited controls are unavailable.
3. Given an authorized password replacement, when it completes, then login works with the new password and repeated startup does not reset it.

## L2-009: Create and validate lead contacts
**Traces to:** L1-003

Lead records must include first name and last name (1–100 characters each), email
(1–254 characters with a syntactically valid address), optional phone (at most 32
characters), and one category: Create, Communication, City, Prayer, or Event.
Phone must accept international prefixes and ordinary spaces, parentheses, and
hyphens; no phone number can be fabricated. Duplicate normalized email/category
pairs are prohibited; the same email in different categories is allowed.

**Acceptance Criteria:**
1. Given an administrator enters valid details for each category, when save is submitted, then each new record receives an ID and persists after reload, including an omitted phone as empty.
2. Given an empty required field, an exceeded field limit, malformed email, or unknown category, when submitted, then validation V rejects it with the affected field identified.
3. Given an existing email/category pair, when a second record uses case/whitespace variations of that pair, then it returns 409; changing the category permits creation.
4. Given international formatted phone text within its limit, when saved, then the entered value is preserved rather than rejected for lacking a local format.
5. Given profile R, when a lead is created, then all fields, category options, validation errors, and submit/cancel controls remain usable at every width.

## L2-010: Lead directory, details, search, and filtering
**Traces to:** L1-003

The directory must show names, category, email, and phone with a readable empty
phone value and link to lead details. Search must use a trimmed, case-insensitive
substring of first name, last name, combined full name, email, or phone; category
filter and search must combine using AND. Default ordering is last name, first
name, then stable ID. Pagination follows L2-045.

**Acceptance Criteria:**
1. Given stored records, when the directory and a detail view are opened, then their saved values are shown and an absent phone is labeled as not provided.
2. Given matching and nonmatching records, when search text and a category are applied, then only records satisfying both appear, across all pages, in the specified order.
3. Given zero matches, when results render, then a zero-result message and a clear-filter control are shown; clearing restores the unfiltered directory.
4. Given a nonexistent lead ID, when details are requested, then the API returns 404 and the UI offers navigation back to the directory.
5. Given profile R, when directory search, category filtering, pagination, and details are used, then contact values and controls remain readable and reachable at every width.

## L2-011: Edit lead contacts
**Traces to:** L1-003

Administrators must edit all contact fields and category using L2-009 validation
and concurrency protection from L2-041.

**Acceptance Criteria:**
1. Given a saved lead, when valid changed details or category are submitted, then the API and directory/detail views show the new values after reload.
2. Given editing would duplicate an email/category pair or violates validation, when submitted, then it fails without changing the saved record and valid form input remains.
3. Given editing is canceled, when the directory is reopened, then the original saved values remain.
4. Given profile R, when a lead is edited, then the form, errors, and save/cancel outcomes work at every width.

## L2-012: Delete leads without unrelated data loss
**Traces to:** L1-003

Lead deletion must require confirmation naming the contact and must be blocked
while any workspace references the lead as its responsible contact.

**Acceptance Criteria:**
1. Given a deletion dialog, when canceled, then no request mutates the contact; when confirmed for an unreferenced lead, then the lead disappears after reload.
2. Given a referenced lead, when deletion is confirmed or called directly, then the API returns 409 and identifies that ownership must first be reassigned or removed.
3. Given a contact shares an email with a user or has formerly owned work, when its permitted deletion completes, then user accounts, work, and sprint history remain intact.
4. Given profile R, when deletion is reviewed and confirmed or canceled, then the named record and both choices remain readable and reachable.

## L2-014: Project workspace management
**Traces to:** L1-004

Administrators must create, list, read, and edit workspaces with a required name
(1–200 characters), optional description (up to 10,000 characters), delivery mode
(Kanban or Scrum), and optional existing responsible lead contact. Workspace
deletion must require confirmation and be blocked while work or sprint history
exists. Initial mode selection is required; later changes follow L2-027.

**Acceptance Criteria:**
1. Given valid workspace data, when an administrator saves it, then its ID, name, description, mode, and responsible contact persist and appear in workspace navigation.
2. Given an empty name, exceeded limit, unknown mode, or nonexistent contact, when submitted, then validation V rejects it without creating or modifying a workspace.
3. Given an empty workspace, when deletion is confirmed, then it is removed; given work or sprint history exists, then deletion returns 409 without cascading.
4. Given profile R, when workspace listing, creation, editing, or deletion is used, then controls, labels, and confirmation remain usable at every width.

## L2-015: Create and navigate the work hierarchy
**Traces to:** L1-004

Every work item must have an ID, type, workspace, required title (1–200 characters),
optional description (up to 10,000 characters), status, and order. New items default
to To Do. Initiatives have no parent; epics require an initiative, stories an epic,
and tasks a story, within the same workspace.

**Acceptance Criteria:**
1. Given a workspace, when an initiative and its epic, story, and task are created in sequence, then each item persists with the correct parent and can be opened from its parent or hierarchy navigation.
2. Given a missing required parent, wrong parent type, cross-workspace parent, or a parent assigned to an initiative, when saved, then validation V rejects the link.
3. Given a work item, when its detail view opens, then its type, workspace, parent path, title, description, status, assignee, and children are visible; missing optional values are identified as unset.
4. Given profile R, when the full hierarchy is created or navigated, then parent context and creation/detail controls remain readable and reachable at every width.

## L2-016: Edit, assign, and reparent work
**Traces to:** L1-004

Permitted users must edit item title, description, status, optional active-user
assignee, optional start/due dates, and optional nonnegative integer story estimate.
Due date must not precede start date when both exist. Reparenting must preserve item
identity and valid same-workspace links and append the item after the target
parent's existing children. Item type and workspace must not change. Estimates
are accepted only for stories.

**Acceptance Criteria:**
1. Given valid edits or an active-user assignment, when saved, then the updated fields persist and all views show them after reload; clearing optional fields removes their values.
2. Given an inactive/nonexistent assignee, negative/fractional estimate, invalid status, or due date before start, when submitted, then validation V rejects it.
3. Given a valid same-type parent in the same workspace, when reparenting is saved, then the item and descendants retain their IDs, field values, and sprint membership under the new path.
4. Given a wrong-type or cross-workspace target, when reparenting is submitted, then it is rejected and the old hierarchy remains intact.
5. Given profile R, when work is edited, assigned, or reparented, then each control and outcome is reachable at every width.

---

## L2-017: Stable prioritization and backlog ordering
**Traces to:** L1-004

Permitted users must reorder siblings at each hierarchy level and prioritize a
workspace's story backlog independently of sibling ordering. Reordering must
preserve stable item IDs and persist a deterministic order without duplicates.

**Acceptance Criteria:**
1. Given ordered sibling items, when one moves before or after another sibling, then all siblings remain present exactly once in the saved order after reload.
2. Given stories from different epics in one workspace, when their backlog priority changes, then backlog order persists without changing their parents or sibling order.
3. Given an out-of-workspace item or invalid target position, when submitted, then validation V rejects the operation without partial reordering.
4. Given profile R or keyboard-only use, when priority is changed with move controls, then the same saved ordering can be achieved without dragging.

## L2-018: Safe work-item deletion
**Traces to:** L1-004

Only administrators must delete work, after confirmation naming the item.
Deletion must be blocked while children exist or a story belongs to a planned or
active sprint. Closed sprint history must survive a later permitted deletion.

**Acceptance Criteria:**
1. Given an item with children, when deletion is submitted, then it returns 409 until the children are explicitly removed or reparented.
2. Given an otherwise deletable story in an open sprint, when deletion is submitted, then it returns 409 until membership is removed through a permitted sprint action.
3. Given a deletable leaf item, when confirmation is canceled, then it remains; when confirmed, then it disappears from live views and counts after reload.
4. Given a story included in closed sprint history, when it is later deleted after satisfying the other rules, then the recorded sprint outcome remains readable.
5. Given profile R, when deletion is attempted, then confirmation, blocked-reason messages, and cancellation work at every width.

## L2-019: Kanban board and story details
**Traces to:** L1-005

A Kanban workspace must display To Do, In Progress, and Done columns with stories
as cards. Each card must show title, assignee or Unassigned, and completed/total
task counts. Opening a card must show its tasks and hierarchy path. Card ordering
must be stable per column and independent of backlog priority.

**Acceptance Criteria:**
1. Given stories in each status, when the board opens, then each story appears exactly once in its matching column, with persisted order and accurate task counts.
2. Given a story card, when opened, then its details, parent epic/initiative, and tasks can be read and edited according to profile P.
3. Given an empty column or empty workspace, when the board renders, then the column remains visible and an appropriate empty state is shown.
4. Given profile R, when all columns and story details are accessed, then the board scrolls within its region when necessary and the page itself does not scroll horizontally.

---

## L2-020: Persisted and accessible Kanban moves
**Traces to:** L1-005

Permitted users must move stories between statuses and reorder cards using both
pointer dragging and labeled move controls. The API must apply status and column
order atomically. Failed or conflicting moves must restore the last saved view.

**Acceptance Criteria:**
1. Given a story card, when moved to another column or position by pointer, then its status/order persist and reload shows it once at the saved location.
2. Given keyboard-only or touch interaction at profile R, when destination and position are selected through move controls, then the same persisted result is achieved without dragging.
3. Given a rejected, conflicting, or unavailable save, when a move fails, then the UI restores the last known persisted position, explains the failure, and offers retry or reload.
4. Given a destination outside the story's workspace or an unknown status, when a move is submitted, then validation V rejects it without changing status or order.

---

## L2-021: Explicit story completion with unfinished tasks
**Traces to:** L1-005

Marking a story Done while it contains unfinished tasks must require an explicit
confirmation showing the unfinished count. Confirmation must not silently mark
tasks Done. The rule applies to Kanban, Scrum, and direct story status edits.

**Acceptance Criteria:**
1. Given all tasks are Done or no tasks exist, when a story is marked Done, then completion persists without the unfinished-task confirmation.
2. Given unfinished tasks, when a story is marked Done without confirmation, then the API returns 409 and the UI identifies the remaining task count.
3. Given the unfinished-task confirmation, when canceled, then status remains unchanged; when explicitly confirmed, then the story becomes Done while task statuses remain unchanged.
4. Given profile R or keyboard-only use, when the confirmation is reviewed, then its count and both choices are readable and reachable.

---

## L2-022: Plan sprints and allocate stories
**Traces to:** L1-006

Scrum workspaces must support planned sprints with a name (1–200 characters),
goal (1–2,000 characters), start date, and end date on or after start. Dates use
Toronto calendar dates. A story must belong to at most one planned/active sprint
at a time; tasks inherit membership. Permitted users can edit planned sprints
and add/remove unfinished stories. Done stories cannot be newly allocated.

**Acceptance Criteria:**
1. Given valid sprint fields and unallocated unfinished stories from the workspace, when the plan is saved, then fields, story membership, and inherited task membership persist.
2. Given missing/over-limit fields, end before start, a foreign-workspace story, or a Done story, when submitted, then validation V rejects the plan without partial allocation.
3. Given a story already in another planned/active sprint, when allocated again, then it returns 409; removal from its existing sprint makes it available for allocation.
4. Given a planned sprint, when its valid goal/dates or membership are changed, then those changes persist and removed stories return to the unallocated backlog.
5. Given profile R, when sprint fields and story selection are edited, then the complete planning workflow remains usable at every width.

---

## L2-023: Start and manage the active sprint
**Traces to:** L1-006

A workspace must have at most one active sprint. Starting must transition a
planned sprint to Active and record the start instant. Active sprint scope can be
changed explicitly by permitted users, without losing the recorded initial scope.

**Acceptance Criteria:**
1. Given a valid planned sprint and no active sprint, when start is confirmed, then it becomes Active, records a start instant and initial story scope, and opens its board.
2. Given an active sprint already exists, when another start is submitted, then it returns 409 and neither sprint changes; concurrent starts yield at most one active sprint.
3. Given an active sprint, when a permitted user explicitly adds or removes an eligible unfinished story, then current scope updates and the history identifies the scope change and actor.
4. Given a closed sprint, when start or scope changes are requested, then they return 409 and history remains unchanged.
5. Given profile R, when sprint start or active scope changes are confirmed, then the choices and resulting status remain accessible at every width.

---

## L2-024: Execute work on the sprint board
**Traces to:** L1-006

An active sprint board must show only its currently allocated stories, using the
same status columns, task counts, and accessible move behavior as Kanban. Story
status is shared across backlog, hierarchy, and sprint views.

**Acceptance Criteria:**
1. Given allocated and unallocated stories, when the active sprint board opens, then only allocated stories appear, once each, in their status columns.
2. Given a permitted card move or task update, when saved, then the sprint board, story details, and workspace views reflect the same persisted status and task counts.
3. Given unfinished tasks, when a sprint story is marked Done, then the confirmation rule in L2-021 applies.
4. Given profile R with keyboard or touch navigation, when sprint work is viewed and moved, then all columns, tasks, and move controls are reachable without page horizontal scrolling or required dragging.

## L2-025: Close sprints and resolve unfinished work
**Traces to:** L1-006

Closing an active sprint must require a disposition for every unfinished story:
return to backlog or move to an eligible planned sprint in the same workspace.
Closure must be atomic, record a close instant and story outcomes, and preserve
completed stories' association with the closed sprint.

**Acceptance Criteria:**
1. Given unfinished stories without dispositions, when closure is submitted, then it returns 400 identifying each unresolved story and the sprint remains Active.
2. Given a valid disposition for every unfinished story, when closure is confirmed, then the sprint becomes Closed and each unfinished story moves to its selected destination with unchanged work status.
3. Given an invalid destination or a concurrent membership change, when closure is submitted, then it returns 400 or 409 and neither sprint nor story membership is partially changed.
4. Given only Done stories, when closure is confirmed, then it closes with no carryover and retains completion outcomes for all stories.
5. Given profile R, when carryover and closure are reviewed, then every story, destination choice, cancel control, and confirmation is usable at every width.

---

## L2-026: Preserve and display sprint history
**Traces to:** L1-006

Closed sprint history must preserve its name, goal, planned dates, actual start/
close instants, initial and final scope, and story IDs, titles, statuses, and
carryover destinations as recorded at closure. Later edits, reparenting, or
permitted deletions must not rewrite these recorded outcomes.

**Acceptance Criteria:**
1. Given a closed sprint, when history opens, then the recorded fields and completed/unfinished outcomes are readable and agree with its closure snapshot.
2. Given a story is later edited, deleted, or completed in another sprint, when the old sprint is read, then its original recorded title and closure status remain unchanged.
3. Given a request to edit a closed sprint, when submitted, then it returns 409 rather than altering history.
4. Given profile R, when sprint history and carryover destinations are inspected, then outcomes remain readable at every width and deleted destinations are identified without broken navigation.

## L2-027: Change delivery mode safely
**Traces to:** L1-006

Only administrators must switch workspace mode. An active sprint must block a
mode change. Kanban mode must preserve planned/closed sprints but disable their
execution until returning to Scrum; work remains available on the Kanban board.

**Acceptance Criteria:**
1. Given no active sprint, when an administrator switches mode, then hierarchy IDs, statuses, ordering, assignments, and sprint plans/history are preserved after reload.
2. Given an active sprint, when mode change is requested, then it returns 409 explaining that the sprint must be closed first.
3. Given Kanban mode with preserved sprint plans, when start or allocation is requested, then it returns 409; switching back to Scrum restores access to those plans and history.
4. Given profile R, when mode selection and a blocked-change message appear, then they remain readable and reachable at every width.

## L2-031: Reliable form submission and destructive confirmations
**Traces to:** L1-008

Forms must expose field-specific validation, retain input on rejected saves,
prevent duplicate submission while pending, display results, and confirm leaving
with unsaved edits. Destructive confirmations must name the affected item.

**Acceptance Criteria:**
1. Given an invalid form, when submitted, then field messages are shown and focus moves to the first invalid field or linked error summary without clearing other values.
2. Given a pending save, when submit is clicked repeatedly, then only one request is sent and visible progress indicates that the operation is pending.
3. Given a failed save, when the error renders, then valid input remains and retry is possible; successful save shows confirmation and updates persisted views.
4. Given dirty form input, when in-app navigation or cancel would discard it, then confirmation permits staying with input intact or leaving without saving.
5. Given any destructive action at profile R, when its dialog opens, then the record name and clear cancel/confirm choices fit and remain accessible.

## L2-032: Empty, loading, error, and visual feedback states
**Traces to:** L1-008

Production views must use the application design tokens and consistent typography,
spacing, focus, form, and status patterns. Loading, empty data, zero search
results, and request errors must be distinguishable and offer relevant actions.
Visual review is for application UX; design artifacts themselves remain exempt
from automated tests.

**Acceptance Criteria:**
1. Given a delayed request, when the view opens, then it shows a loading indicator rather than a misleading empty state until the request finishes.
2. Given a genuinely empty collection, when loaded, then it explains the next permitted action; users without create permission are not offered that action.
3. Given a request failure, when displayed, then a readable message and retry control appear; retry updates the view when the API recovers.
4. Given production screens at profile R, when visually reviewed, then spacing, headings, fields, status indicators, and focus use the documented design language and no text or controls overlap.

## L2-033: Keyboard operation and focus management
**Traces to:** L1-009

Every application workflow must be operable by keyboard without required dragging.
Focus must remain visible, follow a logical sequence, and be managed when dialogs
open/close and routed content changes.

**Acceptance Criteria:**
1. Given keyboard-only use, when login, account/lead/work CRUD, backlog moves, board moves, and sprint operations are completed, then Tab, Shift+Tab, Enter, Space, and labeled move controls reach all required actions.
2. Given a modal dialog, when it opens, then focus moves inside; Tab stays within it; cancel or permitted Escape closes it and restores focus to its trigger or a surviving contextual control.
3. Given profile R, when focus traverses menus, forms, cards, and dialogs, then a visible focus indicator appears and focused controls are not hidden behind fixed content.
4. Given a route change, when the destination loads, then focus moves to the destination heading or main content rather than remaining in a closed navigation menu.

## L2-034: Accessible labels, structure, and announcements
**Traces to:** L1-009

Application controls must expose programmatic names and roles. Inputs must have
associated labels; field errors must identify their inputs. Pages must expose
main/navigation regions and a coherent heading hierarchy. Asynchronous outcomes
must be announced without relying only on visual changes.

**Acceptance Criteria:**
1. Given each production form, when inspected through the accessibility tree, then every input has a label, required state, and associated error text when invalid.
2. Given a board move, saved form, failed save, or loaded search result, when its outcome occurs, then an accessible status/error announcement identifies the result without unnecessarily moving focus.
3. Given a page, when navigated by headings and landmarks, then its purpose, main content, and primary navigation are identifiable without reading decorative content.
4. Given profile R, when labels or icon-only controls are inspected, then their accessible names remain present in both compact and expanded layouts.

## L2-035: Contrast, zoom, touch, and non-color meaning
**Traces to:** L1-009

The application must meet the proposed WCAG 2.2 AA target. Normal text must reach
4.5:1 contrast, large text 3:1, and essential control boundaries/focus/status
graphics 3:1 against adjacent colors. Status must include text or another
non-color cue. Primary touch controls must provide at least 44×44 CSS-pixel
targets; other controls must satisfy applicable AA target-size requirements.

**Acceptance Criteria:**
1. Given production screens in their supported visual states, when contrast is measured, then text and essential control indicators meet the ratios above.
2. Given color is unavailable to the user, when work status, error, or success appears, then its meaning remains understandable through text or non-color cues.
3. Given 200% text zoom and the profile R widths, when essential workflows are used, then content is not lost and controls remain operable with vertical scrolling permitted.
4. Given touch use at 320px or 375px, when navigation, save/cancel, card move, and dialog controls are used, then primary target sizes satisfy the stated minimum and no action requires hover.

## L2-036: Credential, token, and secret protection
**Traces to:** L1-010

Passwords must be stored using a maintained password-hashing mechanism with
per-password salts. JWT signing material and bootstrap secrets must come from
external configuration. Production authentication must use HTTPS. Tokens must
not be persisted in browser local/session storage, URLs, or contact data.

**Acceptance Criteria:**
1. Given two provisioned accounts with the same password, when stored credentials are inspected in an isolated acceptance environment, then neither stores plaintext and the hashes differ while both authenticate correctly.
2. Given signing material is missing or invalid, when the application starts, then readiness fails and no token is issued with fallback or hard-coded signing material.
3. Given a production HTTP request, when it attempts authentication or protected access, then it is rejected or redirected to HTTPS before a credential/token exchange succeeds.
4. Given a signed-in client, when browser storage, navigation URLs, and application logs are inspected, then access tokens are absent except from their intended in-memory session and authentication response.
5. Given logs and error responses after successful/failed login, when reviewed, then credentials, hashes, JWTs, signing keys, and bootstrap values are not disclosed.

## L2-037: Safe input handling and API boundaries
**Traces to:** L1-010

The backend must independently enforce validation V, permission profile P, and
record relationship rules. Data access must treat user text as data, and Angular
must render user text without executing markup or scripts. CORS must permit only
configured frontend origins. Public registration must not be exposed.

**Acceptance Criteria:**
1. Given SQL-like text in search or descriptions, when submitted, then it is treated as text and neither exposes extra records nor changes unrelated data.
2. Given script/HTML text in a saved description or title, when rendered, then it does not execute and is displayed as non-executable content.
3. Given an unconfigured browser origin, when it attempts a cross-origin API request, then the response does not grant CORS access; a configured origin can perform permitted calls.
4. Given a forged UI request containing unauthorized role/status or relationship fields, when received, then the backend rejects forbidden changes rather than trusting hidden controls.
5. Given an unauthenticated user attempts public account registration, when the request is made, then no user account is provisioned.

## L2-038: Authentication abuse throttling
**Traces to:** L1-010

Proposed baseline: five failed login attempts for a normalized email within a
rolling 15-minute window must cause subsequent attempts to return 429 for 15
minutes after the fifth failure. The same policy must apply to nonexistent
accounts. Throttling must not deactivate or demote the designated administrator.

**Acceptance Criteria:**
1. Given fewer than five failures in the window, when invalid login is submitted, then it returns the generic 401 response and increments the failure count.
2. Given the fifth failure occurred, when another attempt for that normalized email is made before the throttle expires, then it returns 429 with retry timing and issues no token.
3. Given the throttle interval has expired, when valid credentials are submitted, then login succeeds and the failure count resets.
4. Given email case/whitespace variants or an unknown email, when attempts accumulate, then normalization and throttle thresholds behave identically without revealing account existence.
5. Given throttling appears under profile R, when the login view displays it, then retry guidance is readable and entered email remains available.

## L2-039: Audit security and data mutations
**Traces to:** L1-010

The system must record UTC timestamp, actor ID when known, operation, entity type/
ID, outcome, and correlation ID for account/permission changes, contact/workspace/
work mutations, board/sprint mutations, successful login, denied access, and
throttling. Audit data must exclude secrets and contact payloads. Only
administrators must access audit records; audit mutation endpoints must be absent.

**Acceptance Criteria:**
1. Given a successful mutation, when its audit record is read, then the actor, operation, target ID, timestamp, and success outcome match the committed change.
2. Given a rejected permission change, login denial, or throttled attempt, when audited, then its outcome and correlation ID are recorded without password, token, or contact details.
3. Given a transaction for a business mutation fails, when persistence is inspected, then no successful-mutation audit entry exists for that uncommitted change.
4. Given a Collaborator or unauthenticated caller, when audit data is requested, then access returns 403 or 401; requests to rewrite audit history do not mutate it.

## L2-040: Durable, atomic business changes
**Traces to:** L1-011

Committed account, contact, hierarchy, ordering, board, and sprint changes must
survive restart. Operations spanning multiple records must commit entirely or
leave all affected business records unchanged.

**Acceptance Criteria:**
1. Given successful mutations in every listed area, when the application restarts against the same SQL database, then their values and relationships are preserved.
2. Given a failure partway through a board reorder, hierarchy change, sprint start, or sprint closure, when the operation ends, then no partial business change is visible.
3. Given deletion of an unrelated contact or work item, when committed, then unrelated users, work, and recorded sprint outcomes remain unchanged.
4. Given a data-changing response reports success, when the same record is read in a new request, then its committed result is visible.

## L2-041: Conflict detection and relational constraints
**Traces to:** L1-011

Edits must carry a record version or equivalent concurrency condition. SQL
constraints must protect normalized account emails, lead email/category pairs,
parent references, open sprint membership, and active sprint exclusivity. Caller
errors must produce validation/conflict responses rather than generic failures.

**Acceptance Criteria:**
1. Given two clients read the same version, when one saves and the other submits stale edits, then the latter receives 409 and cannot silently overwrite the first change.
2. Given conflicting requests race for a unique identity, parent relationship, sprint allocation, or active sprint, when both finish, then persistent state satisfies the relevant rule and a losing request receives 400 or 409.
3. Given the UI receives an edit conflict under profile R, when it displays the result, then it preserves the user's unsaved input and offers reload for comparison without automatic resubmission.
4. Given concurrent parent deletion and child creation, when requests finish, then no orphan child exists; one operation is rejected with a readable conflict or reference error.

## L2-042: Repeatable initialization and health status
**Traces to:** L1-012

Deployment must support repeatable migrations followed by required seeding.
Readiness must succeed only after required schema, SQL access, and administrator
initialization succeed. Liveness must distinguish an alive process from readiness.

**Acceptance Criteria:**
1. Given an empty database, when deployment initialization runs, then migrations and seed complete before readiness reports HTTP 200.
2. Given the same initialized database, when initialization repeats, then it preserves data and reports success without applying the same migration twice.
3. Given unavailable SQL, incompatible schema, or failed required seed, when readiness is requested, then it returns 503 without secrets or connection strings.
4. Given the process is alive but SQL is unavailable, when liveness and readiness are requested, then liveness remains 200 while readiness is 503.

## L2-043: Diagnosable errors and request correlation
**Traces to:** L1-012

The API must return a correlation ID for unexpected failures and write structured
diagnostic records containing operation, UTC time, outcome, and that same ID.
Users must receive useful error categories without internal stack traces or
secret values. Production logs and diagnostics must be restricted operational data.

**Acceptance Criteria:**
1. Given an unexpected server error, when a request fails, then the API returns a generic 500 response with a correlation ID and a matching diagnostic event exists.
2. Given validation, permission, missing-record, or concurrency errors, when they occur, then the response uses validation V's specific status rather than an undifferentiated 500.
3. Given diagnostic records for failed initialization and requests, when reviewed, then their IDs and operation names support investigation without credentials, tokens, connection strings, or contact payloads.
4. Given an application error at profile R, when shown to the user, then the readable message, retry/navigation action, and support correlation ID fit the screen.

## L2-044: Backup and restore readiness
**Traces to:** L1-012

Release documentation must identify the chosen SQL provider, backup commands,
schedule/retention, storage access, restore steps, responsible operator, and
verification procedure. A restore rehearsal must recover a populated database
into a separate environment before release. Recovery must not reset existing
administrator passwords or rewrite historical sprint results.

**Acceptance Criteria:**
1. Given a database containing accounts, all lead categories, complete work hierarchies, boards, and sprint history, when a backup is restored into an isolated environment, then all IDs, relationships, ordering, and historical outcomes match the backup point.
2. Given the restored administrator has a changed password, when the restored app initializes, then that password remains valid and the account retains highest capabilities.
3. Given an operator following the documented commands, when the rehearsal runs, then the procedure records start/end times, verification results, backup point, and any failures without altering the source environment.
4. Given release readiness review, when the recovery runbook is inspected, then every listed operational field is present and the latest rehearsal result is recorded.

## L2-045: Bounded collection loading
**Traces to:** L1-013

Directories, workspace lists, backlogs, and history lists must default to 25 records
per page and cap requested page size at 100. Invalid sizes must return 400.
Results must include total matching count and stable ordering. Boards/hierarchies
must load bounded batches of at most 100 and allow access to every matching item;
counts must reflect the full dataset rather than just loaded records.

**Acceptance Criteria:**
1. Given more than 100 matching records, when default and explicit pages are requested, then page sizes and total counts are correct and every record is reachable without duplication under unchanged data.
2. Given zero, negative, or greater-than-100 page size, when submitted, then the API returns 400 with a page-size message.
3. Given filtered/search results, when filters change, then pagination resets to the first page and total count reflects only matching records.
4. Given a large board or hierarchy at profile R, when successive batches are loaded, then all items remain reachable, full counts remain accurate, and no unbounded initial collection response is required.

## L2-046: Measurable initial performance budgets
**Traces to:** L1-013

The proposed acceptance workload is 1,000 leads and 10,000 work items across 50
workspaces with both delivery modes and sprint history. Measure on separate app
and SQL instances, each with 4 vCPUs and 8 GiB RAM, SSD storage, and ≤2 ms app/SQL
round-trip latency. The browser profile is current installed Chromium, four
logical CPU cores, 8 GiB RAM, 20 Mbps network throughput and 40 ms API round-trip
latency. Record exact versions, configuration, fixture, and hardware in results.

Run 25 authenticated concurrent sessions at one request per second each for 10
minutes after one minute of warm-up: 60% reads, 40% permitted writes. Reads must
include directory/search, backlog, board batches, and sprint history; writes must
include lead/work edits, card moves, and sprint planning. Report p95 by operation
class rather than pooling all operations. These budgets are proposed targets,
not measured claims.

**Acceptance Criteria:**
1. Given the stated workload/environment, when the load run completes, then each read/write operation class has p95 server time ≤500 ms, excluding client/network time, with no unexpected 5xx responses or data-integrity failures.
2. Given the browser profile and cold frontend cache, when home, leads, backlog, and active board are opened, then the initial visible content and essential controls become usable in ≤2.5 seconds at p95 across 30 runs per view.
3. Given sustained 25-session load, when the run ends, then stored state satisfies hierarchy, identity, ordering, and sprint rules and results include operation counts and latency percentiles.
4. Given a different deployment or smaller measured environment, when results are reported, then its configuration is recorded separately and is not labeled as passing this profile without running the stated checks.
