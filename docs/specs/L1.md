# L1 - High-Level Requirements

**Status:** Confirmed by the product owner; elaborated in [L2](L2.md).  
**Product:** Mission Control for FaithTech Toronto.  
**Baseline:** [PRD](../PRD.md) and [agent instructions](../../AGENTS.md).

The backend must use .NET, the frontend must use Angular, and the application
must own SQL-backed accounts, authorization, and JWT issuance. Detailed behaviors
and Given-When-Then acceptance criteria are recorded in L2.
PRD proposals remain proposals; scope confirmation does not approve them implicitly.

Mocks and the design system are design artifacts. ATDD does not apply to their
development, and no tests must be written for them. Production application
acceptance tests must identify the L2 requirements they cover in comments.

## L1-001: Accounts and access control

The system must authenticate users, support sign-in and sign-out, and enforce
application-owned permissions on every protected operation. Administrators must
be able to provision accounts and manage access. Lead responsibilities must remain
distinct from application permissions, and lead contacts must not require accounts.

## L1-002: Always-available administrator

The system must always maintain Quinntyne Brown's designated account with the
highest available capabilities, using the bootstrap identity and initial password
specified in the PRD. Initialization must be repeatable without duplicate accounts
or resetting an existing password. The application must prevent removal,
deactivation, or demotion of this account.

## L1-003: Team lead directory

The system must allow authorized users to create, read, update, and delete leads
for Create, Communication, City, Prayer, and Event responsibilities. It must capture
first name, last name, phone number, and email and support finding leads by their
contact details and category. Quinntyne Brown must be identifiable as the City Lead.

## L1-004: Project organization and work hierarchy

The system must organize project workspaces and maintain the hierarchy Initiative
→ Epic → Story → Task. Authorized users must be able to create, read, update,
delete, prioritize, assign, and navigate work while preserving valid parent-child
relationships and preventing accidental loss of related work.

## L1-005: Kanban delivery

The system must support Kanban workspaces with an ordered backlog and a board
showing work by status. Authorized users must be able to move and reorder work,
inspect its tasks, and see persisted progress. Board operations must be usable
without drag-and-drop.

## L1-006: Scrum delivery

The system must support Scrum workspaces with backlog prioritization, sprint
planning, sprint goals and dates, an active sprint board, sprint closure, and
readable sprint history. It must handle unfinished work explicitly and preserve
project data and history when delivery mode changes.

## L1-007: Overview and navigation

The system must provide a home workspace showing lead category coverage, projects,
work progress, and active sprints. Users must be able to navigate from these
summaries to the underlying records and retain context within the work hierarchy.
Summaries and navigation must reflect the user's permissions.

## L1-008: Responsive and pleasant user experience

The application must make every user workflow usable from extra small through
extra large screens. It must use clear visual hierarchy, generous white space,
consistent navigation and forms, and useful empty, loading, success, and error
states. Failed operations must preserve user input and support recovery.

## L1-009: Accessible interactions

The application must support keyboard navigation, visible focus, assistive
technology, legible contrast, non-color status indicators, and touch interactions.
Users must be able to complete essential workflows without relying on pointer
dragging. The PRD's proposed WCAG 2.2 AA target remains subject to confirmation.

## L1-010: Security and data protection

The system must protect credentials, sessions, and contact information; validate
inputs; prevent unauthorized access; and limit authentication abuse. Sensitive
values must not leak through errors or logs. Security-relevant events and data
changes must be auditable without recording secret values or contact payloads.

## L1-011: Durable and consistent data

The system must preserve committed changes across restarts, maintain valid and
unique account identities and work relationships, and apply related changes
consistently. Concurrent updates must not silently overwrite newer work. Deletions
must preserve unrelated accounts, contacts, work, and historical records.

## L1-012: Operational readiness and recovery

The system must support repeatable initialization and database changes, visible
health and readiness status, diagnosable failures, and documented backup and restore.
Initialization failures must not be reported as successful startup. Recovery must
restore accounts, leads, project work, and sprint history.

## L1-013: Performance and scale

The application must keep directory, backlog, board, and form workflows responsive
under the agreed initial data volume and concurrent use. Large collections must
be bounded or paginated. L2 must define measurable API and page performance
criteria using an explicit environment and workload; PRD budgets remain proposals.

## L1-014: Design artifacts

The project must provide a standalone design system with authoritative design
tokens and visual examples, and mocks for reviewing proposed application workflows.
These artifacts must communicate the application's responsive visual language.
Their development must not use ATDD, and no tests must be written for them.

## Scope and decisions for L2

The initial scope is FaithTech Toronto lead management and agile project delivery.
The PRD's deferred capabilities remain outside this release.

L2 elaboration must resolve or explicitly retain the PRD's proposed permission
matrix, lead cardinality and required fields, separate City contact seed, story
board cards, sprint rules, session lifecycle, SQL provider, deployment choices,
accessibility target, and performance fixture. These choices must not be treated
as confirmed merely because they appeared in the initial PRD.
